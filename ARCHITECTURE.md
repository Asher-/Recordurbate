## Overview

Recordurbate is a daemon that monitors a list of Chaturbate streamers and
automatically records their live streams. It runs as a
background process (via UNIX double-fork daemonization) and exposes an IPC
interface over TCP for runtime management (add/remove streamers, start/stop,
list status).

The daemon spawns one `recorder.py` subprocess per online streamer. The
recorder resolves the room's playlists with yt-dlp, downloads every video and
audio segment itself, and has a local ffmpeg mux them into
`videos/<name>/<title>.ts`. The daemon monitors these processes, validates
that each launch started, and relaunches recorders when streams end.

The daemon listens on a fixed localhost TCP port, so the CLI connects to it
directly, and a second daemon cannot bind the port while the first holds it.

## Process Hierarchy

When the daemon is running and recording a streamer, the process tree looks
like this:

```
launchd (PID 1)
└── python cli.py start          (daemon, double-forked, PPID=1)
    │
    │   [threads inside daemon process]
    │   ├── main thread           (waiting for run loop thread to finish)
    │   ├── run loop thread       (non-daemon, iterates streamers every 60s)
    │   ├── IPC server thread     (daemon thread, accept loop)
    │   ├── IPC handler threads   (daemon threads, one per active connection)
    │   └── streamer threads      (daemon threads, one per streamer, manage a recorder)
    │
    ├── recorder.py <streamer_a>  (own session, PGID=own PID, Ss)
    │   ├── yt-dlp --dump-single-json   (seconds, while resolving the room)
    │   └── ffmpeg                (local muxer: pipes in, MPEG-TS out)
    ├── recorder.py <streamer_b>
    │   └── ffmpeg
    └── ...
```

Key relationships:

- **Daemon → recorder.py**: Parent-child. The daemon spawns `recorder.py` via
  `subprocess.Popen`. Each recorder runs in its own session
  (`start_new_session=True`), making it a session leader (stat `Ss`).
- **recorder.py → yt-dlp**: Parent-child, short-lived. The recorder runs yt-dlp
  only to resolve the room's playlists, and waits for it to exit.
- **recorder.py → ffmpeg**: Parent-child. The recorder feeds downloaded
  segments to ffmpeg through pipes and appends ffmpeg's stdout to the
  recording. ffmpeg opens no network connection; it exits at end of input when
  the recorder closes the pipes, and the recorder reaps it.
- **Daemon threads → recorder.py**: Each streamer thread holds a `Popen`
  reference to its recorder and is responsible for reaping it via `wait()`.

## Thread Model

The daemon process contains several categories of threads:

| Thread              | Daemon? | Count | Purpose                                                      |
| :------------------ | :------ | :---- | :----------------------------------------------------------- |
| Main thread         | —       |     1 | Waits for run loop thread (keeps process alive)              |
| Run loop thread     | No      |     1 | Iterates streamers, launches missing streams, sleeps 60s     |
| IPC accept thread   | Yes     |     1 | Accepts TCP connections, dispatches to handler threads       |
| IPC handler threads | Yes     | 0–N   | One per active CLI connection, processes a single command    |
| Streamer threads    | Yes     | 0–N   | One per streamer, manages the recorder for that streamer     |

**Non-daemon** threads prevent the process from exiting. The run loop thread is
non-daemon, so the process stays alive as long as the run loop is active. All
other threads are daemon threads — they are killed when the last non-daemon
thread exits.

**Concurrency note**: There is no mutex protecting `self.streamers` or
individual `Streamer` fields. The run loop thread reads `streamer.stream` to
decide whether to call `start()`, while the streamer thread writes to
`streamer.stream` and `streamer.started`. This is safe in practice because:

- Only one streamer thread exists per streamer at a time.
- The run loop only checks `streamer.stream` (truthiness) and calls `start()`
  if it's `None`.
- The streamer thread sets `self.stream` at the beginning and clears it at the
  end.

## Module Reference

### cli.py

Entry point. Invoked as `python cli.py <command> [args]`.

**Interpreter**: before its project imports, which load third-party packages,
`cli.py` compares `realpath(sys.prefix)` with `realpath(venv/)` beside it. When
they differ and `venv/bin/python` exists, it calls
`os.execv(venv/bin/python, ...)` with the same arguments, so `./cli.py` runs
under the project venv without activation.

**Flow for `enable`, `disable`, `status`**: `service()` runs `service.sh <command>`
from the directory containing `cli.py` and exits with its return code;
`service.sh` implements the launchd management (see
[launchd Integration](#launchd-integration)).

**Flow for `start`**:

1. Creates a `Daemon` instance and calls `daemon.start()`.
2. The daemon binds its fixed port before forking or running (see
   [Daemon Address](#daemon-address)). If another daemon holds the port, it
   prints "Already started." and exits with status 1.
3. The parent and intermediate fork processes exit via `sys.exit(0)` inside
   `daemonize()`. Only the final child continues.

**Flow for all other commands** (`stop`, `add`, `del`, `list`, etc.):

1. Opens a `SocketClient` connection to the daemon at `IpcConfig.host` and
   `IpcConfig.port`, raising `ValueError("Daemon is not running.")` when the
   connection is refused.
2. Sends the command string over TCP.
3. Reads and prints the response until the terminator sentinel is received.

**Global state**: `socket_client` is lazily initialized on the first IPC call
and reused for the lifetime of the CLI process.

### daemon.py

The `Daemon` class manages the entire daemon lifecycle.

**`__init__`**: Initializes logger, loads config, creates `Streamer` objects
for each name in the config, registers SIGINT/SIGTERM handlers.

**`daemonize()`**: Classic UNIX double-fork:

1. Creates the `SocketServer` and binds its fixed port, so a second daemon
   prints "Already started." and exits here, in the process the user started.
2. First `os.fork()` — parent exits, child continues.
3. Second `os.fork()` — intermediate child exits, grandchild continues.
4. Grandchild is the daemon: detached from terminal, PPID becomes 1.
5. Starts the IPC socket server's accept loop on the inherited socket.
6. Closes stdin/stdout/stderr and points fds 0-2 at `/dev/null`, releasing any
   terminal or pipe the caller attached, to complete daemonization.

**`run()`**: Starts the run loop in a non-daemon thread:

```
while self.pid:
    reload_config()                    # pick up config changes
    for each streamer:
        if not self.pid: break         # stop/handoff ends the pass
        if not streaming: start()      # launch recorder.py
        rate_limit_sleep()
    sleep 60s (in 1s intervals, checking self.pid)
```

**`stop()`**: Sets `self.pid = None`, which causes the run loop to exit. The
run loop's cleanup phase calls `streamer.stop()` on all streamers. Then
`sys.exit(0)`.

**`reload_config()`**: Reloads `config.json` every loop iteration (when
`auto_reload_config` is true). Preserves existing `Streamer` objects for names
that still exist, creates new ones for additions, and drops removed ones.

**`ipc()`**: Command dispatcher. Parses the command string and routes to the
appropriate method (`stop`, `add_streamer`, `delete_streamer`,
`list_streamers`, etc.).

### streamer.py

The `Streamer` class manages a single streamer's `recorder.py` process.

**Fields**:

| Field     | Type            | Description                                             |
| :-------- | :-------------- | :------------------------------------------------------ |
| `name`    | `str`           | Chaturbate username                                     |
| `daemon`  | `Daemon`        | Back-reference to parent daemon                         |
| `stream`  | `Popen or None` | Active recorder.py subprocess, or `None` if not running |
| `started` | `bool`          | `True` if stream validated and actively recording       |

**`start()`**: Spawns a daemon thread (`stream_thread`) that:

1. Launches `[sys.executable, "recorder.py", "https://chaturbate.com/<name>/"]`
   via `subprocess.Popen` with:
   - `start_new_session=True` — isolates child in its own session/process
     group so it doesn't receive signals meant for the daemon.
   - `stdout` and `stderr` appended to `configs/capture-<name>.log`.
2. Polls every 1s for up to `process_poll_wait_time` (default 15s) to detect
   early exit (e.g., streamer offline). Breaks immediately if the process
   exits.
3. If the process is still alive, calls `recorder_ready()`, which waits up to
   90s for the recorder's `Recording <name> to <path>` line in this launch's
   capture log, then `ensure_valid_stream()`. Without that line the launch did
   not start recording.
4. If valid, calls `finalize_prior_parts()` to strip `.part` from this
   streamer's files last written before the recorder was launched (leftovers
   of yt-dlp recordings that were never finalized), then sets
   `started = True` and blocks in `proc.wait()` until the recorder exits.
5. On exit, calls `cleanup_ffmpeg()`, then `stop(signal_child=False)`.

**`launch_error()`**: After a launch that did not start recording, reads what
the recorder and its yt-dlp lookup wrote to `configs/capture-<name>.log` for
this launch. A last `ERROR:` line naming a room state (offline, private show,
away, password protected, hidden) returns `None`, since only the site can
report one. Anything else, including no error at all, is returned for
`Daemon.record_launch()` to count.

**`ensure_valid_stream()`**: Returns whether the launched or adopted process
is alive, via `pid.process_active()`.

**`cleanup_ffmpeg()`**: Called after the recorder exits. Finds any ffmpeg
process whose command line contains `/<streamer_name>/` and sends `SIGTERM`.
Only an ffmpeg started by an adopted yt-dlp from an older daemon matches;
`recorder.py`'s muxer reads from pipes and never names the streamer.

**`stop(signal_child)`**:

- If `signal_child=True` and `started`: sends `SIGINT` to the recorder, then
  `wait()` for graceful shutdown.
- Regardless: checks `poll()` — if the child is still alive, sends `SIGTERM`
  via `terminate()` and `wait()`. This is the safety net for hung processes.
- Sets `self.stream = None`.

### recorder.py

Records one room into a growing MPEG-TS file:
`recorder.py https://chaturbate.com/<name>/`.

Chaturbate serves LL-HLS with video and audio as separate fMP4 playlists of
1.6s segments and a window of about 8s. The recorder:

1. Runs `<youtube-dl_cmd> --config-location <youtube-dl_config>
   --dump-single-json <url>` with a 60s timeout and passes yt-dlp's stderr on
   to the capture log. Any failure of this first lookup (offline, private,
   network error, unreadable output) ends the recorder with status 1.
2. Takes the title and one playlist URL per entry of `requested_formats`, and
   opens `videos/<name>/<title>.ts` for appending.
3. Every 1s, loads each playlist and its `EXT-X-MAP` init segment, then
   fetches every full `EXTINF` segment it has not yet written, in
   media-sequence order. `EXT-X-PART` parts are ignored.
4. Feeds each track to the `Muxer`: a local
   `ffmpeg -f mov -i pipe:<fd> … -map <i> -c copy -f mpegts pipe:1`, whose
   stdout is appended to the `.ts`. Each input has its own queue and writer
   thread, so a fetch never waits on ffmpeg.

| Event                                                 | Response                                                           |
| :---------------------------------------------------- | :----------------------------------------------------------------- |
| Segment fetch fails 3 times (3s/5s timeouts), or once with HTTP 403/404/410 | Log the segment as failed and continue with the next one |
| Segments left the playlist before fetching            | Log the lost range and continue                                    |
| Not every playlist loaded for 15s                     | Re-resolve through yt-dlp (at most once per 15s)                   |
| Re-resolution: yt-dlp names a room state              | Exit                                                               |
| Re-resolution: any other yt-dlp failure               | Log it and keep recording                                          |
| Re-resolution: a different number of tracks          | Restart the muxer with the new tracks, appending to the same file  |
| Init segment bytes differ from the last ones fetched  | Restart the muxer, appending to the same file                      |
| ffmpeg exits                                          | Restart the muxer, appending to the same file                      |
| Media sequence restarts                               | Resume from the playlist's first segment                           |
| No new segment for 120s                               | Exit                                                               |
| `EXT-X-ENDLIST`                                       | Exit                                                               |
| SIGINT / SIGTERM                                      | Stop between fetch attempts, close the muxer and exit              |

SIGINT and SIGTERM are checked before every playlist, init and segment fetch
attempt and every 0.5s of a yt-dlp lookup. Closing the muxer gives ffmpeg 3s
to drain its inputs and 3s to exit before it is killed.

On exit an empty output file is deleted. ffprobe reads the `.ts` while it is
being written, and the file tolerates gaps and muxer restarts.

### pid.py

Process utility functions using `psutil`.

**`process_active(pid)`**: Returns `True` if the PID exists and is not in
`STATUS_DEAD` or `STATUS_ZOMBIE` state.

**`get_pid_by_name_and_args(process_name, args_substring, exe_path)`**: Iterates
all system processes to find one matching by name (case-insensitive), optionally
filtering by a substring in the command-line arguments and/or executable path.
Returns the first matching PID or `None`. Used to find ffmpeg processes
associated with a specific streamer.

### ipc/server.py

`SocketServer` — the daemon-side TCP server for IPC.

**Lifecycle**:

1. `__init__` — resolves hostname/IP, stores daemon reference.
2. `bind()` — creates a TCP socket with `SO_REUSEADDR`, binds it to the given
   port, listens, and sets a 2s accept timeout. When the port is already bound
   (`EADDRINUSE`) it prints "Already started." and exits with status 1; any
   other bind error is raised.
3. `start()` — starts the accept loop.
4. `loop()` — runs in a daemon thread. Calls `accept()` in a loop (with 2s
   timeout so it can check `self.daemon.pid` for shutdown). Each accepted
   connection is dispatched to `handle_connection()` in its own daemon thread.
5. `handle_connection()` — sets a 10s recv timeout on the client socket, reads
   the command, creates a `ClientResponse`, dispatches to `daemon.ipc()`.
   Uses `try/finally` to guarantee `client_response.close()` (sends
   terminator) and `connected_socket.close()` always execute, even if the
   command handler throws.

**Error handling**: Catches `socket.timeout`, `ConnectionResetError`, and all
other exceptions per-connection. A failing command never kills the accept loop.

---

### ipc/client.py

`SocketClient` — the CLI-side TCP client.

**`start()`**: Connects to the daemon with a 30s timeout.

**`ipc(command_string)`**: Sends the command, then enters a read loop:

- Uses `select.select()` with a 30s timeout to wait for data.
- If timeout expires, prints "Timed out waiting for response." and exits.
- If `recv()` returns empty bytes (server closed connection), exits.
- If the terminator sentinel (`0xDEADBEEF`) is found at the end of received
  data, strips it and exits after printing any remaining data.
- Catches `ValueError`/`OSError` from `select` for connection loss.

---

### ipc/client\_response.py

`ClientResponse` — wraps a connected socket for server→client communication.

- **`print(string)`** — encodes and sends a string (with trailing newline).
- **`close()`** — sends the terminator bytes (`0xDEADBEEF`), signaling end of
  response.

---

### ipc/terminator.py

`Terminator` — defines the end-of-message sentinel.

```python
bytes      = b'\xDE\xAD\xBE\xEF'   # 4-byte sentinel
byte_array = bytearray(bytes)        # for comparison
length     = 4                        # for slicing
```

The terminator is appended to every server response. The client scans the tail
of each `recv()` for this pattern to know when the response is complete.

### ipc/ipc\_config.py

`IpcConfig` — the daemon's fixed IPC address.

```python
host = "127.0.0.1"
port = 47391
```

The daemon binds this address and the CLI connects to it, so both agree on
where the daemon listens without any lookup (see

## Daemonization

The daemon uses the classic UNIX double-fork pattern:

```
cli.py start
  │
  ├── ipc_client.bind()               # bind the fixed port; exit if it is held
  │
  ├── os.fork() ──► Parent (original process): sys.exit(0)
  │
  └── Child 1
        │
        ├── os.fork() ──► Child 1: sys.exit(0)
        │
        └── Child 2 (the daemon)
              │
              ├── self.pid = os.getpid()
              ├── ipc_client.start()        # start the accept loop
              ├── close stdin/stdout/stderr; fds 0-2 → /dev/null
              └── return to start() → run()
```

The double fork ensures the daemon:

- Is not a session leader (can't accidentally acquire a controlling terminal).
- Has PPID=1 (adopted by init/launchd).
- Has no controlling terminal.

After daemonization, `start()` calls `run()`, which starts the non-daemon run
loop thread. The main thread then falls off the end of `cli.py` and enters
Python's shutdown sequence, where it waits for the non-daemon run loop thread
to finish (which only happens when `self.pid` is set to `None`).

## Streamer Lifecycle

```
                    ┌─────────────────────────────────────────────┐
                    │              Run Loop (60s cycle)            │
                    │                                             │
                    │  for each streamer:                         │
                    │      if streamer.stream is None:            │
                    │          streamer.start()                   │
                    └──────────────┬──────────────────────────────┘
                                   │
                           streamer.start()
                                   │
                    ┌──────────────▼──────────────────────────────┐
                    │          stream_thread (daemon thread)       │
                    │                                             │
                    │  1. Popen(recorder.py, new session)         │
                    │  2. Poll every 1s up to poll_wait_time      │
                    │     └─ break early if process exits         │
                    │  3. If still alive:                         │
                    │     ├─ recorder_ready()                     │
                    │     │  └─ "Recording" line within 90s       │
                    │     └─ ensure_valid_stream()                │
                    │        └─ recorder alive → True             │
                    │  4. If valid:                               │
                    │     ├─ finalize_prior_parts()               │
                    │     ├─ started = True                       │
                    │     ├─ proc.wait() (until recorder exits)   │
                    │     └─ cleanup_ffmpeg()                     │
                    │  5. stop(signal_child=False)                │
                    │     ├─ If child still alive: terminate+wait │
                    │     └─ stream = None                        │
                    └─────────────────────────────────────────────┘
                                   │
                           (thread exits)
                                   │
                    ┌──────────────▼──────────────────────────────┐
                    │  Next run loop iteration sees               │
                    │  streamer.stream is None → start() again    │
                    └─────────────────────────────────────────────┘
```

**Timing**: after the poll loop (≤15s), `recorder_ready()` waits up to
`READY_TIMEOUT` (90s) for the recorder's line. The yt-dlp lookup can take
longer than the poll loop; for an offline streamer `recorder.py` then exits
during the readiness wait, which detects the exit within 1s.

## Stream Validation

A launch counts as started only when `recorder_ready()` finds
`[recorder <time>] Recording <name> to <path>` in this launch's part of
`configs/capture-<name>.log` (read from the offset taken before `Popen`).
`recorder.py` writes that line once yt-dlp has resolved the room; until then
it may still exit reporting a room state. `recorder_ready()` polls the log
every 1s and returns `False` when the recorder exits, the streamer is stopped,
or `READY_TIMEOUT` (90s, above `recorder.py`'s 60s lookup limit) passes.

`ensure_valid_stream` then returns whether the launched (or adopted) process
is still alive, checked with `process_active()` on its PID.

`adopt()` checks only `ensure_valid_stream`, so it validates on liveness alone.
A handoff can catch a recorder inside its yt-dlp lookup (up to 60s); the new
daemon adopts it and logs `Adopted stream for <name> validated.` even if the
lookup then reports the room offline. That recorder exits, the adopted thread
ends and clears `stream`, and the next run loop relaunches the room. Adoption
records no launch and finalizes no `.part` files, so the log line is the only
effect.

## IPC Protocol

### Daemon Address

The daemon listens on a fixed address, `IpcConfig.host`:`IpcConfig.port`
(`127.0.0.1:47391`), and the CLI connects to it directly.

The port also keeps the daemon single. Binding it fails with `EADDRINUSE` while
a daemon holds it, so a second daemon prints "Already started." and exits
before it forks or runs. The kernel releases the port when the holding process
exits, however it exits, so nothing stale is left behind; `SO_REUSEADDR` lets
the next daemon bind while connections the old one closed are still in
`TIME_WAIT`.

The port lies below macOS's ephemeral range (49152–65535), so the kernel never
assigns it to an outgoing connection.

### TCP Socket Protocol

The protocol is simple request-response over a single TCP connection:

1. **Client → Server**: Raw UTF-8 command string (≤512 bytes). Examples:
   `"stop"`, `"add username"`, `"list online"`.
2. **Server → Client**: Zero or more UTF-8 string chunks (each ≤512 bytes),
   terminated by the 4-byte sentinel `0xDEADBEEF`.

The terminator allows variable-length responses. The client reads until it sees
the sentinel at the end of a `recv()` chunk.

**Timeouts**:

| Component      | Timeout | Purpose                                     |
| :------------- | :------ | :------------------------------------------ |
| Server accept  | 2s      | Allows shutdown check every 2s              |

## Signal Handling

### Daemon Signals

The daemon registers handlers for:

- **SIGINT** — calls `daemon.stop()` (graceful shutdown).
- **SIGTERM** — calls `daemon.stop()` (graceful shutdown).

`stop()` sets `self.pid = None`, causing the run loop to exit. The run loop's
cleanup phase iterates all streamers and calls `streamer.stop()` with
`signal_child=True`, which sends SIGINT to each recorder and waits for it to
exit.

### Child Process Isolation

Each recorder child is isolated from the daemon's signal environment:

- **`start_new_session=True`** — creates a new session and process group. The
  child will not receive signals sent to the daemon's process group (e.g.,
  terminal SIGINT from Ctrl+C). The daemon can still send signals to specific
  PIDs via `Popen.send_signal()`.

- **SIGINT and SIGTERM end a recording cleanly** — `recorder.py` handles both
  by finishing the current fetch, closing its muxer's input pipes so ffmpeg
  flushes the last packets and exits, reaping ffmpeg, and exiting. If the
  recorder doesn't respond, `stop()` escalates to SIGTERM via
  `Popen.terminate()`.

## Operational Guide

### service.sh vs cli.py

There are two ways to invoke Recordurbate commands. Both accept the same
arguments; the difference is how they handle the Python virtual environment.

**`service.sh`** (recommended) activates the venv transparently before
dispatching to `cli.py`. It also provides `enable`/`disable`/`status` commands
for managing the macOS launchd service. Use this for day-to-day operation.

**`cli.py`** is the Python entry point. It imports project dependencies
(`psutil`) directly, so when launched with any interpreter other
than `venv/bin/python` it re-execs itself under `venv/bin/python` first; no
activation is needed. `./cli.py enable`, `./cli.py disable` and
`./cli.py status` run `service.sh` with the same subcommand. Use this from any
shell, with or without the venv activated, or on systems where `service.sh` is
not available.

All examples in this section use `cli.py` for clarity (the direct Python
interface is what ARCHITECTURE.md documents), but `./service.sh <cmd>` works
identically for any command shown.

### Starting the Daemon

```bash
./service.sh start          # recommended (handles venv)
python cli.py start         # direct (re-execs under venv)
```

The process double-forks and returns immediately. The daemon runs in the
background. Check the log to confirm:

```bash
tail -f configs/rb.log
```

### Foreground Mode

The `--foreground` flag prevents the daemon from double-forking. The process
stays attached to the terminal instead of detaching into the background:

```bash
python cli.py start --foreground
```

This is used by launchd, which expects to supervise the process directly (see
[launchd Integration](#launchd-integration)). It is also useful for debugging —
the daemon's log output goes to the terminal and Ctrl+C shuts it down cleanly.

Internally, when `--foreground` is set, `daemon.start()` skips the double-fork
sequence entirely and runs the main loop in the calling process.

### Stopping the Daemon

```bash
./service.sh stop
python cli.py stop
```

Sends the `stop` command via IPC. The daemon gracefully shuts down: signals all
recorders with SIGINT, waits for them to exit, then exits itself.

### Managing Streamers

```bash
./service.sh add <username>         # Add a streamer
./service.sh del <username>         # Remove a streamer (stops recording)
./service.sh list                   # List all streamers (* = recording, - = offline)
./service.sh list online            # List currently recording
./service.sh list offline           # List currently offline
./service.sh import <file>          # Import streamer names from file (one per line)
./service.sh export [file]          # Export streamer names to file
```

Changes made via `add`/`del`/`import` are persisted to `configs/config.json`
immediately.

Since recorder processes run in their own sessions, they don't appear in
`ps -u`. Use:

```bash

ps aux | grep recorder.py

ps -eo pid,ppid,stat,command | grep -E 'recordurbate|recorder.py|yt-dlp|ffmpeg'

# Sample a hung process (macOS) for stack trace
sample <PID> 1
```

| Code | Meaning                                        |

| `Ss` | Sleeping, session leader                       |

### launchd Integration

`service.sh` manages the launchd plist lifecycle:

```bash
./service.sh enable       # generate plist, install to ~/Library/LaunchAgents/, load
./service.sh disable      # unload and remove
./service.sh status       # show loaded/running state, PID and last exit
```

`enable` generates `launchd.plist` from the current project directory (so paths
are always correct), copies it to `~/Library/LaunchAgents/com.recordurbate.daemon.plist`,
and loads it via `launchctl`.

The plist starts the daemon in **foreground mode** (`--foreground`), so launchd
supervises the process directly — no double-fork. This means:

- launchd sees the daemon's actual PID and can monitor it.
- `KeepAlive: false` — launchd does not auto-restart, but
  `ThrottleInterval: 30` ensures a 30s delay if the process exits and is
  restarted manually.
- `RunAtLoad: true` — the daemon starts automatically at login.
- Logs go to `~/Library/Logs/Recordurbate/launchd.stdout.log` and
  `~/Library/Logs/Recordurbate/launchd.stderr.log`.

## Known Behaviors

### yt-dlp Internal Deadlocks

yt-dlp occasionally deadlocks on internal Python threading locks (observed via
`sample` showing the main thread blocked on `lock_PyThread_acquire_lock` →
`_pthread_cond_wait`). This is a yt-dlp bug, not a Recordurbate bug.

yt-dlp now only resolves a room, so a deadlock can only stall that lookup.
`recorder.py` runs it with a 60s timeout: at the first launch a stalled
lookup makes the recorder exit, and during a recording it counts as a failed
re-resolution, which keeps the recording open and is retried 15s later.

### Session Isolation and ps Visibility

Recorder processes run in their own sessions (`start_new_session=True`), which
means:

- They have **no controlling terminal**.
- They do **not** appear in `ps -u` (which filters by terminal).
- They **do** appear in `ps aux`, `ps -A`, and `ps -eo ...`.
- Their `STAT` column shows `Ss` (sleeping, session leader).

This isolation prevents recorders from receiving terminal signals (Ctrl+C)
that are meant for the daemon. The daemon can still send signals to specific
recorder PIDs.

### Offline Streamer Cycling

When a streamer is offline, the recorder's yt-dlp lookup reports the room
state and the recorder exits. The launch poll or the readiness wait detects
this within 1 additional second. The streamer thread cleans up and sets
`stream = None`. On the next run loop iteration (up to 60s later), the daemon
re-launches the recorder for that streamer.

With 96+ streamers and `rate_limit_time: 0`, all offline streamers are cycled
rapidly. Each cycle creates a short-lived recorder that exits immediately.
This is normal and expected.

### Unreachable Site Warning

A launch that starts recording or reports a room state has reached the site.
Any other outcome is a miss, and `Daemon.record_launch()` counts misses in a
row. When the count reaches the number of streamers it writes one line to
`configs/rb.log` with yt-dlp's latest error, and one more line when a launch
next gets through. Single misses are routine, and a launch the daemon stopped
itself is not counted.

## In-Place Upgrade (Handoff)

The daemon supports in-place upgrades: a new daemon process takes over
monitoring of existing recorder subprocesses from the old daemon, allowing code
updates without interrupting active recordings.

### Upgrade Lifecycle

```
CLI: python cli.py upgrade
  │
  ├── 1. Send "handoff" command to running daemon via IPC
  │
  ├── 2. Old daemon receives "handoff":
  │      ├── Sets _handoff = True
  │      ├── Sets self.pid = None (stops run loop)
  │      ├── Run loop exits WITHOUT calling streamer.stop()
  │      ├── recorder children are reparented to PID 1 (launchd)
  │      └── Old daemon process exits
  │
  ├── 3. CLI polls until the old daemon's port can be bound (up to 15s)
  │
  ├── 4. CLI creates new Daemon() and calls daemon.start()
  │      ├── Binds the fixed IPC port
  │      └── Double-fork daemonization
  │
  └── 5. New daemon's run() calls adopt_existing():
         ├── find_running_ytdlp() scans all processes for recorder.py
         │   (or a yt-dlp left by an older daemon) with chaturbate.com
         │   URLs in their command lines
         ├── For each match in the streamer config:
         │   └── streamer.adopt(pid) wraps the PID in AdoptedProcess
         │       and starts a monitoring thread
         └── Unmatched processes are logged but ignored
```

### AdoptedProcess

`AdoptedProcess` (in `pid.py`) wraps a bare PID with the same interface as
`subprocess.Popen`, allowing `Streamer` to use either interchangeably:

| Method           | Popen                       | AdoptedProcess                    |
| :--------------- | :-------------------------- | :-------------------------------- |
| `poll()`         | Checks child exit status    | `psutil.Process.status()`         |
| `wait(timeout)`  | `os.waitpid()` (child only) | `psutil.Process.wait()` (any PID) |
| `send_signal(s)` | `os.kill(self.pid, s)`      | `os.kill(self.pid, s)`            |
| `terminate()`    | Sends SIGTERM               | Sends SIGTERM                     |

`wait(timeout)` translates `psutil.TimeoutExpired` into
`subprocess.TimeoutExpired` so `Streamer.stop()` exception handling works
unchanged.

### New IPC Command

| Command   | Handler            | Description                                 |
| :-------- | :----------------- | :------------------------------------------ |
| `handoff` | `daemon.handoff()` | Exit daemon without killing child processes |

### New CLI Command

```bash
python cli.py upgrade
```

Performs a full in-place upgrade: handoff → wait → start. Active recordings
continue uninterrupted through the new daemon.

### Files Changed

**`pid.py`**:

- `AdoptedProcess` class — Popen-compatible wrapper using `psutil.Process`.
- `find_running_ytdlp()` — scans system processes for `recorder.py`, yt-dlp
  or yt_dlp with chaturbate URLs, skipping `recorder.py`'s own
  `--dump-single-json` lookup, and returns a `{streamer_name: pid}` dict.

**`streamer.py`**:

- `adopt(pid)` — creates a daemon thread that wraps the PID in
  `AdoptedProcess`, validates the stream, and blocks on `wait()` until the
  recorder exits. On exit, cleans up ffmpeg and resets `self.stream`.

**`daemon.py`**:

- `_handoff` flag — when `True`, the run loop cleanup phase skips
  `streamer.stop()`, leaving children running.
- `handoff()` — sets `_handoff = True`, stops the run loop, exits.
- `adopt_existing()` — called at the start of `run()`. Scans for running
  recorders (and yt-dlp processes left by an older daemon) and calls
  `streamer.adopt(pid)` for each match.
- IPC dispatch — routes `"handoff"` to `daemon.handoff()`.

**`cli.py`**:

- `upgrade()` — sends `"handoff"` via IPC, polls `port_in_use()` until the old
  daemon has released its port, then starts a new daemon.

## Stream End

`stream_thread` and `adopted_thread` block in `proc.wait()` until the
recorder exits, then run `cleanup_ffmpeg()` and `stop(signal_child=False)`.
The daemon lists no directory and watches no file to decide that a recording
has stalled; `recorder.py` ends a stalled recording itself (see
[recorder.py](#recorderpy)):

| Layer            | Where         | Mechanism                                                 |
| :--------------- | :------------ | :-------------------------------------------------------- |
| Segment fetching | `recorder.py` | 3s connect / 5s read timeouts, 3 attempts, gap on failure |
| Re-resolution    | `recorder.py` | fresh playlist URLs from yt-dlp after 15s unreachable     |
| Give-up          | `recorder.py` | exit after 120s without a new segment                     |

A yt-dlp process adopted from an older daemon has no give-up of its own; its
thread waits until that process exits.
